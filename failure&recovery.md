# Failure and Recovery — RideEase

Identify at least 5 possible failures. At least one must relate to each area below:
- Application/server
- Database
- Network
- Storage
- Security

| Failure | Impact | Detection | Recovery |
|---|---|---|---|
| **Application/server** | The Flask process (`app.py`) crashes or hangs due to an unhandled exception (e.g., a malformed request to the fare/translation route), stopping the whole app — booking, chat, and fare estimation all become unavailable. | Terminal/console shows the process has stopped; the browser can no longer reach `http://127.0.0.1:5000`; requests time out or return connection-refused errors. | Restart the Flask server manually (`python app.py`) or use a process manager (e.g., Flask's debug reloader, or a tool like Watchdog/systemd in a deployed setting) to auto-restart on crash; add try/except blocks around route handlers to prevent full crashes from single bad requests. |
| **Database** | RideEase currently has no persistent database — all ride/session data lives in memory or the browser session. A server restart or crash wipes all active ride data, chat history, and fare estimates instantly. | Not directly "detected" since there's no DB layer, but the absence shows up as riders losing chat history, route, or fare details immediately after a refresh or server restart. | Short-term: no recovery possible for lost session data since none is persisted (expected limitation of the demo). Long-term (per project's future scope): introduce a real database (e.g., SQLite/PostgreSQL) with regular backups and session persistence. |
| **Network** | Calls to external APIs — OSRM (routing) or Google Gemini (translation) — fail due to no internet connection, API downtime, or rate limiting. Riders can't get a route, fare estimate, or translated chat. | Frontend shows a failed/blank map route, a stuck "calculating fare" state, or chat messages that never translate; backend logs show request timeouts or non-200 responses from OSRM/Gemini endpoints. | Implement retry logic with exponential backoff for API calls; show a graceful fallback message ("Route unavailable, try again"); cache last-known route/fare briefly; fall back to a straight-line distance estimate if OSRM is unreachable. |
| **Storage** | The `.env` file (containing the Gemini API key) is missing, corrupted, or misconfigured, or static assets (`script.js`, `style.css`) fail to load, breaking the map, styling, or chat logic client-side. | App fails to start or throws an authentication error the first time a translation request is made; console logs show "GEMINI_API_KEY not found" or similar; browser dev tools show 404s for missing CSS/JS files. | Recreate `.env` from `.env.example` and re-add the API key; verify file permissions and that `python-dotenv` is loading the file correctly; restore `static/` folder from version control (e.g., git) if static files are deleted or corrupted. |
| **Security** | The Gemini API key in `.env` is accidentally committed to a public repo, or exposed via a misconfigured route, allowing unauthorized use of the translation API (and potential billing/quota abuse). | Manual code review, git history audit, or automated secret-scanning tools (e.g., GitHub secret scanning, truffleHog) flag the key in a commit. | Immediately revoke/rotate the exposed key in Google AI Studio; generate a new key and update `.env`; add `.env` to `.gitignore`; audit git history and scrub the key from past commits if needed. |
